# ADR 0036：持久 Work 任务与运行状态边界

- 状态：Accepted
- 文档类型：ADR
- 维护者：system_architect
- 决策日期：2026-10-12
- 关联：[计划 0014](../plans/0014-general-agent-automation.md)、[工作流架构](../../neuroagent/workflow/README.md)、[Work 双 Agent ADR](0024-work-dual-agents.md)

## 背景

Work 需要跨用户消息、页面关闭和 Worker 完成事件持续推进目标。现有会话、计划、审批、运行、QC 与产物各有持久记录；如果在任务层复制它们的生命周期，会产生冲突状态和重复授权风险。

## 决策

增加应用层持久 `WorkTask` 与 `TaskStep`，只记录用户目标、步骤进展、等待条件、恢复位置、累计预算、幂等事件消费身份，以及对权威对象的引用。它们不复制 Run、PlanRevision、ApprovalRecord、QC 或 Artifact 状态，也不创建运行重试。

运行事件仅作为唤醒提示。任务被唤醒后必须重新读取关联运行、输入修订、QC 和产物的权威记录，再决定下一步。重复或乱序事件通过持久去重身份安全消费；用户消息和系统恢复使用不同来源类型，系统事件不得伪装成用户输入。

Worker 继续负责作业领取、租约、attempt、有限重试和运行终态。任务控制器不得在等待既有运行时另建 Run 来“恢复”。新执行仍沿用现有批准方案和逐次确认边界；继续任务不隐含新增科研选择或执行授权。

任务可以达到 `waiting_user`、`waiting_run`、`waiting_dependency`、`completed`、`blocked` 或 `cancelled` 等状态。等待和完成条件属于目标推进状态，不改变被引用运行的状态。并发推进须使用版本检查、有限领取租约和幂等提交；事务保存在现有 SQLite 单体中，不增加消息中间件。

## 后果

页面及 API 进程无需保持内存状态即可恢复任务；事件消费者需要在事件之后重新查证事实。任务预算跨角色、重启和事件重放保持不变。任务记录提供推进审计，但 WorkflowInstance 仍是运行生命周期的唯一真源。

若未来要让“继续”自动授权多次真实计算、自动排除受试者或改变方法，必须另行设计授权合同并由用户明确批准。
