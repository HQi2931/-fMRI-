# ADR 0011：Work 对话作为唯一业务入口

## 状态

已接受，2026-09-17。

## 背景

项目原先以总览、数据、方案、运行、QC、统计和扩展分析页面暴露同一组业务能力，同时又在 Agent 中提供 Work 模式。入口重复会造成上下文分离：用户在一处选择项目、在另一处审批计划，刷新或切换会话后很难判断哪个对象和版本正在被操作。自然语言请求也不能安全地直接映射为任意前端组件或执行代码。

## 决策

1. 主导航只保留“对话工作台”。首页和未知地址进入工作台，默认显示 Work；Chat 继续承担 fMRI 专项问答。环境、MATLAB/SPM/DPABI 路径和模型连接集中在 `/settings`。
2. 项目、数据、方案、审批、运行、QC、统计和扩展分析通过 Work 消息内的操作卡片完成。旧业务地址只打开相应能力提示，绝不自动执行。
3. 服务端维护闭集能力目录。自然语言或显式 `card_kind` 只能产生已登记的卡片类型；模型可以提出结构化路由草案，但不能传组件名、脚本、Shell 或 MATLAB 代码。
4. 卡片绑定对话、项目和业务对象，并携带版本。每次提交由服务端检查卡片版本、允许操作、项目归属和既有请求契约，然后调用原有应用服务；不复制科学校验或执行逻辑。
5. 卡片草稿保存在对话消息 payload 中。自动保存不追加消息；批准、启动和其他业务操作追加可审计结果。刷新、切换会话或后台运行时，业务对象状态仍以服务端为准。
6. 科学参数、审批和真实执行继续显式确认。缺少参数时卡片展示未完成字段；失败状态、原因、日志和部分产物原样保留，不由对话层改写成成功。

## 后果

用户在一个连续上下文内完成全部业务操作，后台任务不依赖页面持续打开，且旧链接可以安全迁移。代价是嵌入式业务视图必须支持卡片草稿和操作代理；新增能力也必须先登记卡片类型与允许操作。现有 REST API 保留用于应用服务和兼容集成，Work 卡片层只负责路由、绑定、版本围栏和会话审计。
