# 文档规范

- 状态：Accepted
- 文档类型：Development
- 维护者：documentation_maintainer
- 创建日期：2026-09-23
- 更新日期：2026-09-23
- 适用范围：仓库内所有 Markdown 文档（`docs/`、根级 `*.md`、`neuroagent/*/README.md`、`skills/*/SKILL.md`、`.agents/*.md`）
- 关联：`AGENTS.md` 第 9 节、`.agents/documentation.md`、`docs/README.md`

> 本文件是 `docs/` 的强制规范，由 `scripts/check-docs.ps1` 校验。违反规范的文档不得合并。

## 1. 文档类型与目录

每个文档必须属于且只属于一个类型，目录决定类型，不允许同一主题跨目录重复存在。

| 目录 | 类型 | 回答的问题 | 不写什么 |
| --- | --- | --- | --- |
| `docs/product/` | 产品 | 产品定位、范围、非目标、版本边界 | 实现细节 |
| `docs/architecture/` | 架构 | 分层、边界、数据流、契约关系 | 具体实现进度 |
| `docs/domain/` | 领域 | 科研规则、输入契约、方法学约束 | 部署与运维 |
| `docs/adr/` | 决策 | 背景、决策、后果、替代方案 | 可随时修改的计划 |
| `docs/plans/` | 计划 | 里程碑、任务、验收标准、风险 | 已接受决策的重述 |
| `docs/operations/` | 运维 | 运行、诊断、恢复手册 | 科学方法论证 |
| `docs/development/` | 开发 | 验证事实、发布流程、开发规范 | 产品范围 |
| `docs/api/` | 接口 | 公共 API 契约与错误语义 | 内部实现 |
| `docs/security/` | 安全 | 数据边界、外发策略、密钥处理 | 功能设计 |
| `docs/reviews/` | 审查 | 阶段终审结论与证据快照 | 长期有效的规范 |
| `docs/archive/` | 归档 | 历史文档，只读保留 | 任何当前事实 |

规则：

- 不属于以上类型的阶段性产出（分析稿、实施报告、第三方工作流产物）一律进 `docs/archive/`。
- 归档保留原子目录结构，例如 `docs/archive/plans/0004-release-roadmap.md`。
- 新增顶层目录必须先扩展本表，不得静默创建。

## 2. 文件命名

| 类型 | 命名规则 | 示例 |
| --- | --- | --- |
| ADR | `NNNN-<kebab-title>.md`，四位序号，只追加不复用 | `0014-bounded-tool-loop.md` |
| 计划 | `NNNN-<kebab-title>.md`，四位序号 | `0007-capability-modularization-roadmap.md` |
| 审查报告 | `YYYY-MM-DD-<kebab-title>.md` | `2026-09-23-docs-standardization-audit.md` |
| 其他 | `<kebab-title>.md`，全小写，短横线分词 | `mvp-verification.md` |

禁止在文件名中使用空格、中文、下划线或版本号后缀（如 `-v2`）；版本变化通过新文件或状态字段表达。

## 3. 状态块

每个文档正文必须在其一级标题之后、正文之前包含状态块。状态块统一使用列表项形式，字段名为中文，冒号为全角，顺序固定：

```markdown
- 状态：Implemented
- 文档类型：Architecture
- 维护者：system_architect
- 创建日期：2026-08-06
- 更新日期：2026-09-08
- 关联：`docs/adr/0001-...`
```

- 只有 `状态` 和 `文档类型` 是必填字段；`状态` 之后不得在同一行追加说明。
- ADR 额外必填 `决策日期`；被替代时必须写 `替代关系：已被 ADR NNNN 取代`。
- 计划文档额外必填 `目标里程碑` 和 `验收标准` 所在小节；禁止使用 `目标版本`。

### 3.1 状态枚举（唯一合法取值）

| 取值 | 含义 | 适用于 |
| --- | --- | --- |
| `Draft` | 草稿，明确未生效，不得据此开发 | 全部类型 |
| `Proposed` | 已提出待决，征求评审 | ADR |
| `Review` | 内容完成，等待审查或确认 | 全部类型 |
| `Accepted` | 决策已接受，内容具有约束力 | ADR、计划 |
| `Implementing` | 方案已定，实现进行中 | 计划、架构 |
| `Implemented` | 描述的内容已落地并有验证证据 | 全部类型 |
| `Superseded` | 已被另一文档取代，必须写明取代者 | 全部类型 |
| `Historical` | 仅保留历史背景，不得作为当前依据 | 全部类型 |
| `Rejected` | 提案被否决，保留理由 | ADR |

规则：

- 枚举值一律使用上述英文标识，不在状态行内混用中文枚举。
- 实现进度、代码现状、版本号**不得写入状态行**，必须写在正文相关小节。
- 状态行只允许出现枚举值本身，附加说明放在紧随其后的正文段落，不追加在枚举值之后。
- 状态由维护者在内容变化时同步更新；`Superseded` 和 `Historical` 必须同时提供替代文档或失效说明。

## 5. 禁止发布版本包装

<!-- check-docs:allow-release-framing -->

现行文档不承载发布版本框架。规则：

- `docs/` 下非归档、非 ADR 的文档中禁止出现 `v0.1.0`、`v0.2.0`、`v1.0.0`、`MVP1.0`、`MVP0.1` 等发布版本标识（示例见本行与下行，仅用于说明规则本身）。 <!-- check-docs:allow-release-framing -->
- 禁止用「未发布」「发布条件」「发布阻断项」「打 tag」等发布门禁措辞描述当前状态。
- 表达**当前状态**用状态枚举（`Implemented`／`Implementing`）加正文事实描述，不用版本号。
- 表达**未来工作**用 `Phase N`、`里程碑`、`阶段`、"当前目标"等词，不带版本号。
- 表达**范围边界**用"当前范围／不在当前范围"，不用"某版本的发布范围"。
- 版本号只允许出现在：`docs/adr/` 的历史决策记录、`docs/archive/` 的归档文档、`CHANGELOG.md` 的历史条目，以及机器可读的 API 版本字段和错误码字符串。

理由：版本发布框架会让读者把"当前工作树"当作产品成熟度承诺，而仓库的实际交付单位是阶段（Phase）与里程碑；去版本化后文档描述的是能力是否实现，而不是某个版本是否发布。

## 6. 唯一事实来源

- 每个主题只有一个权威文档，登记在 `docs/README.md` 的权威文档表中。
- 其他文档不得复述权威文档的结论，只能引用。发现复述即视为缺陷，应改为链接。
- 计划文档中的进度陈述与 `docs/development/mvp-verification.md` 冲突时，以后者为准。
- 已接受的 ADR 不改写历史：修正只能通过新 ADR 标记替代。

## 7. 链接与引用

- 文档间引用使用**相对路径** `Markdown 链接`，不使用绝对路径或 URL。
- 引用其他文档的某一小节时使用锚点，并在改写被引用标题时同步更新所有引用点。
- 代码与配置中引用文档时必须给出 `docs/` 相对路径；锚点视为接口，修改前需检索全部引用方。
- **标题冻结清单**：以下文件的标题层级被代码 `evidence_ref` 或 skill 包锚定，禁止在标准化中改写：
  - `docs/architecture/fmri-skill-layer.md`（被 `neuroagent/domain/fmri/skillpacks/builtin.py`、`neuroagent/skills/validation.py` 与 `skills/review-rsfmri-qc/skill.yaml` 引用锚点）
- 归档文档在被引用处必须改为指向替代文档，不得指向归档路径。

## 8. 写作规则（沿用并补强）

- 全部 Markdown 使用 UTF-8。
- 代码标识符、路径、字段名保持英文；面向用户的正文默认中文。
- 区分「目标」「当前实现」「非目标」「未来计划」，不得用现在时描述未实现能力。
- 示例只使用合成或脱敏数据。
- 不复制大段第三方文档；记录来源与版本。
- 状态为 `Draft`、`Proposed`、`Historical` 的文档不得被 `AGENTS.md` 或模块 README 作为实现依据引用。

## 9. 归档规则

满足任一条件即可归档：

1. 已被新文档或 ADR 正式取代。
2. 描述的一次性工作已经完成，且结论已进入权威文档。
3. 自述为编码前的分析稿、临时设计或第三方工作流产出的过程文档。

归档时必须在同一变更内完成：

- 移动文件到 `docs/archive/<原目录>/`。
- 在标题下加入横幅：`> 已归档（YYYY-MM-DD）。原因：<原因>。替代文档：<标题与相对路径>。内容仅作历史参考，不得作为当前实现依据。`
- 将状态改为 `Historical` 或 `Superseded`。
- 修正所有指向该文件的链接：`README.md`、`CHANGELOG.md`、`AGENTS.md`、模块 README、ADR 交叉引用、`skills/*/skill.yaml`、`scripts/*.ps1`。
- 在 `docs/README.md` 的归档清单中登记一行。
- 在 `CHANGELOG.md` 记录用户可见的文档变化。

归档文档除修正链接外不得再编辑内容；发现内容错误时在横幅中说明，不修改原文。

## 10. 文档索引

- `docs/README.md` 是 `docs/` 的唯一索引，必须包含：按类型的目录导航、权威文档表、归档清单、规范入口。
- 索引中的每条链接都必须可解析；失效链接视为门禁失败。
- 新增或归档文档时必须在同一变更内更新索引。

## 11. 校验

- `scripts/check-docs.ps1` 校验：`docs/` 内相对链接可解析、锚点存在、状态枚举合法、状态块字段完整、归档文件无入链、索引覆盖全部现行文档、第 5 节禁用版本标签。
- 校验已纳入 `scripts/quality-gate.ps1`；校验失败不得合并，修复后重跑。
- 需要人工判断的部分（结论是否仍成立、是否与代码一致）由 `documentation_maintainer` 角色复核，不依赖脚本。
