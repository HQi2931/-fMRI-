# 计划 0007：MVP1.0 开发路线图

- 状态：Draft
- 日期：2026-09-07
- 目标版本：`v1.0.0`
- 建议周期：10–12 周，6 个双周迭代内完成
- 架构依据：[MVP1.0 目标架构](../architecture/mvp-1.0-target-architecture.md)
- 决策依据：[ADR 0009](../adr/0009-capability-oriented-modular-monolith.md)

## 里程碑定义

MVP1.0 不是“把所有预览功能都变成真实执行”，而是一套可由研究者稳定完成核心 rs-fMRI 工作的本地产品：

1. 选择并检查 BIDS 或明确的 DPABI 工作副本，冻结可复核的受试者和输入清单。
2. 创建、校验、比较并审批预处理/指标方案。
3. 通过 Mock 或用户明确授权的 MATLAB 后端执行，能取消、恢复、重试并追踪每次 attempt。
4. 查看和审批 QC，显式记录纳入/排除与理由。
5. 完成约定范围内的组统计，预览、导出并离线复核结果包。
6. 使用持久化 Agent Chat/Work 获取有来源的方法解释和受控工作流协助，模型不能绕过确定性服务。

这里把现有 MVP0.1 能力视为技术基线，不改写其正式发布证据。当前分支是否已经发布仍以 tag、CI 和 `docs/development/mvp-verification.md` 为准。

## 范围

### P0：MVP1.0 必须完成

- 能力化模块边界、显式应用服务、窄端口、拆分 routers/contracts 和类型化任务协议。
- BIDS/DPABI-ready 主路径的数据检查、冻结 manifest、工作副本冲突预览和输入哈希复核。
- 已验证范围内的批量预处理与 ALFF/fALFF/ReHo，完整 Artifact lineage、进度、取消、重试和恢复。
- QC 可视化/摘要、人工 revision 和审批门禁。
- 单样本、两独立样本、配对 t 检验，以及当前领域规范已声明的相关/协变量回归；FDR/GRF 与确定性报告。
- Artifact 安全预览/下载、复现包导出和审计。
- Chat/Work 持久化、只读工具审计、本地 RAG、逐次授权联网搜索和明确的模型证据边界。
- Windows 本机安装、升级、备份、恢复、诊断和发布门禁。

### P1：容量允许时纳入

- 真实 ROI 信号提取和结果表导出。
- 基于统计图 NIfTI 网格的 cluster 定位、空间校验和报告整合。
- DPABI 工作副本整理的受控复制执行。
- 计划差异视图、运行间结果比较和更丰富的 QC 图。

### MVP1.0 不包含

- 通用 ML 训练/调参 Runner；保留数据检查和模板能力，真实训练放到 1.x 后续版本。
- 多用户、云部署、PACS、微服务、分布式队列和对象存储。
- 任意 MATLAB/Python/Shell 执行、通用插件市场和长期通用记忆。
- 自动受试者排除、自动显著性优化或临床结论。
- 未经真实 smoke 的所有 DPABI 版本、数据布局、T1 Segment/DARTEL 或多会话协议承诺。

## 分阶段计划

### Phase 0：冻结与修复基线（3–5 天）

目标：把当前在途对话/工作区改动收口为可审查基线，不改变科研语义。

交付：

- 解决 mixin 同名方法类型冲突，格式化当前改动并补足 Agent/AnalysisPage 分支测试。
- 运行完整 `quality-gate.ps1`、生成 OpenAPI/client 并确认工作树无意外生成物。
- 记录最终测试数量、覆盖率、未执行的真实 smoke 和候选树哈希。
- 为 `/api/v1`、数据库迁移、SkillPlan hash、Job payload 和浏览器工作区状态建立兼容快照。

完成标准：本地全门禁通过；无 P0–P2；当前功能和已知限制在 README、验证记录与 CHANGELOG 一致。

### Phase 1：架构解耦（第 1–2 周）

目标：消除阻碍 1.0 迭代的聚合点，同时保持公共行为不变。

交付：

- 抽出内部 `PlanState`、`WorkflowState`、强类型 ID、Artifact 引用和执行结果。
- 按能力拆分 contracts 和 FastAPI routers，旧 import 通过临时重导出兼容。
- 用 `ApplicationServices` + 7 个显式 service 替代多重继承门面。
- 拆分 `RepositoryPort`，实现 `SqliteUnitOfWork` 和能力 repository。
- 增加依赖架构测试、API 快照测试、迁移往返测试和事务原子性测试。

完成标准：Workflow/Execution 不再导入 HTTP/Application DTO；新增一个能力不必修改总 service、总 repository protocol 或总 router；全部旧 API 合同测试通过。

### Phase 2：数据、工作区与方案构建（第 3–4 周）

目标：让真实运行前的输入和方案准备可理解、可比较、可恢复。

交付：

- 工作区检查、项目注册和 manifest 冻结合并为清晰向导，但继续区分只读源目录与可写 DPABI 工作副本。
- 原位运行前展示将创建/复用的 DPABI stage、同名产物冲突、磁盘空间和输入变更。
- 计划表单重构为 feature + reducer + 分段 schema；提供计划差异、参数来源和阻断定位。
- 服务端保存项目当前 revision 关系；浏览器只保存 selected IDs，并支持从 SQLite 完整恢复。
- 明确 MVP1.0 支持的数据矩阵：格式、会话数、每主体 run 数、压缩格式、T1 与无 T1 路径；未验证组合失败关闭。

完成标准：新用户可以从空状态创建并批准计划；刷新、切换项目和浏览器重启不会形成第二事实源；原始数据保持只读。

### Phase 3：执行、Artifact 与 QC（第 5–7 周）

目标：把一次受控真实运行变成可观察、可恢复、可审核的产品流程。

交付：

- `JobEnvelope v1`、typed executor registry、payload 版本迁移和旧任务兼容读取。
- 分步骤进度、心跳、日志游标、取消确认、租约恢复和 attempt 对比；不提供无依据的 ETA。
- 覆盖已承诺预处理/ALFF/fALFF/ReHo 组合的合成 smoke 矩阵和至少一个目标机真实主路径。
- Artifact 目录、角色、checksum、lineage 和 superseded 关系；安全预览/下载 JSON、TSV、Markdown、PNG、日志和允许的 NIfTI。
- QC 摘要、图表、逐受试者检查、revision、纳入/排除理由和审批；任何排除继续要求明确确认。

完成标准：API 或 Worker 被终止后可恢复；取消和超时有界；缺失/旧产物不会登记成功；QC 审批绑定精确 Artifact 与 manifest。

### Phase 4：统计与复现交付（第 7–9 周）

目标：完成从已批准 QC 到可离线复核结果包的组水平分析。

交付：

- 加固三类 t 检验、协变量顺序、对比、尾部和 FDR/GRF 证据。
- 实现并真实验证相关和带协变量回归；不支持的设计在领域层失败关闭。
- 结果页展示设计矩阵、对比、统计/效应图、正负簇表、校正方法、软件证据和限制。
- 导出不可变复现包：manifest、subject order、design、contrast、参数、环境指纹、日志索引、Artifact checksums、Markdown/JSON 报告。
- P1 容量允许时接入真实 ROI 和 cluster 空间定位；与核心统计报告共用 Artifact 合同。

完成标准：所有受试者、影像、组别和协变量显式对齐；结果包在没有数据库的机器上可以验证 checksum 和设计证据；Agent 草稿不会替代确定性报告。

### Phase 5：Agent 与整体 UX（第 9–10 周）

目标：让 Agent 成为受控工作流入口和解释层，而不是另一套运行时。

交付：

- Chat/Work 使用独立的 `AgentService`、Conversation repository 和工具注册表，移除对其他 service 方法的隐式调用。
- 本地 RAG 证据版本、引用、拒答范围和索引更新可见；联网搜索保持逐次授权并记录 URL 与脱敏上下文哈希。
- Work 工具只调用结构化 Query/Command；危险动作返回确认请求，确认后仍走既有应用服务。
- 前端迁移到 feature 目录，增加错误边界、加载/空状态、键盘可访问性和长作业恢复体验。
- 拆分巨型 `App.test.tsx` 为能力级测试，保留少量跨功能旅程测试。

完成标准：对话刷新后可恢复；模型/网络不可用不阻断确定性工作流；工具调用、证据和状态变化可审计。

### Phase 6：发布候选与 1.0（第 11–12 周）

目标：形成可安装、可升级、可回退的 Windows 本地版本。

交付：

- 一键 bootstrap/start/stop/diagnose，生产构建由 FastAPI 提供；明确 Node 仅为开发依赖。
- 数据库升级前自动备份、恢复演练、磁盘不足/路径失效/环境变化诊断。
- Python/Web/安全/依赖审计/Mock E2E/真实 smoke 矩阵全部通过。
- 新用户可用性测试、方法学审核、发布说明、迁移指南、已知限制和 `v1.0.0` tag。

完成标准：至少一台干净 Windows 验证机从安装到报告导出走通；升级和恢复演练通过；发布树与审查树一致。

## 迭代建议

| 迭代 | 主要结果 | 退出门 |
| --- | --- | --- |
| Sprint 1 | Phase 0 + 内部类型/路由切片 | 基线全绿，API 无行为变化 |
| Sprint 2 | 显式服务、窄端口、SQLite UoW | 架构门禁通过，事务回归通过 |
| Sprint 3 | 工作区向导、服务端恢复、计划表单 | 从空状态到批准计划 E2E 通过 |
| Sprint 4 | JobEnvelope、进度恢复、Artifact 访问 | Mock 和合成 MATLAB 执行回归通过 |
| Sprint 5 | QC、统计、复现包、Agent/UX | 核心研究旅程与失败旅程通过 |
| Sprint 6 | smoke 矩阵、安装升级、终审发布 | RC 门禁和干净机器验收通过 |

每个 Sprint 只允许一个主要架构迁移主题；科学行为变化必须单独 PR 和单独方法学审查。

## 质量与发布门禁

- Ruff format/lint、strict mypy、pytest、前端 lint/typecheck/test/build/E2E、依赖审计和仓库安全门禁全部通过。
- 总覆盖率不下降；新增或变更的领域状态、审批、恢复、路径、统计方向和 Artifact 分支必须有针对性测试。
- OpenAPI 生成后无未提交漂移；客户端不重复手写服务端已有 schema。
- Alembic 从空库升级和从 MVP0.1 数据库升级均通过，且恢复脚本完成实际演练。
- Mock 全旅程每次 CI 运行；真实 MATLAB/DPABI 与 Provider smoke 仅在显式授权环境运行并记录证据。
- 发布候选经过架构、后端、前端、QA、MATLAB/DPABI 和 fMRI 方法学复核，无 P0–P2。

## 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| 重构改变计划哈希或科研结果 | 先冻结 golden fixtures；目录移动与科学变化分 PR；旧类型重导出 |
| repository 拆分破坏原子性 | UnitOfWork 作为唯一事务入口；并发、租约和失败注入测试 |
| 前端迁移造成恢复回归 | 服务端真源；保存兼容读取；按旅程建立 E2E 快照 |
| DPABI 环境差异扩大测试矩阵 | 发布明确能力矩阵；按入口指纹和 smoke 声明支持，不按版本名猜测 |
| 原位工作区覆盖已有结果 | 运行前冲突预览；默认隔离模式；覆盖继续逐次确认并记录审计 |
| 1.0 被扩展分析拖延 | P0/P1 严格分离；ML Runner 和非核心兼容性留到 1.x |
| Agent 能力侵入确定性运行 | 工具白名单、结构化 Command、审批绑定和 ToolCall 审计不变 |

## 决策检查点

- Phase 0 后：确认 MVP1.0 P0/P1 范围和 ADR 0009 是否接受。
- Phase 2 后：冻结支持的数据形态和真实 smoke 矩阵。
- Phase 4 后：决定 ROI/cluster 是否进入 1.0 RC，不能影响核心主路径。
- RC 前：确认所有未验证 DPABI 行为和科学限制已在 UI、报告与发布说明中可见。
