## 1. 目标与依据

将“对话规划—方案审查—计算执行—结果查看”设计成连续的用户流程。用户负责科学选择和执行确认，系统负责读取事实、参数映射、规则校验、版本管理和工具协调。

本方案来自 DemoData 单受试者 ALFF 网页真实对话的体验复盘。该次网页运行最终完成计算并进入 QC 审查；早期工具调用失败、回复截断及超时属于此前失败尝试，不能与成功运行混为一谈。当前能力事实仍以[验证记录](../development/mvp-verification.md)为准。本文件保留完整目标设计，阶段实现不代表全部体验已通过验收。

| 草稿操作不直观 | 单选项仍需勾选再确认；“修改要求”主要是关闭窗口并聚焦输入框 | 用户看不到直接修改和差异反馈 |

目前没有足够计时证据证明哈希计算本身是主要耗时。优化首先减少重复扫描、重复模型请求和人工往返；必要的完整性校验仍保留。

## 2. 完整用户旅程

| 阶段 | 系统工作 | 用户看到 | 用户操作 |
| --- | --- | --- | --- |
| 选择数据 | 检查目录、输入配对及可用起始阶段 | 数据概况、访问范围 | 选择工作区，必要时授权文件处理 |
| 描述目标 | 识别指标，保留明确参数 | 简短的任务理解 | 用自然语言描述分析目标 |
| 核实与补充 | 读取元数据，计算派生事实，检查冲突 | 已核实事实与少量关键问题 | 回答无法可靠推断的问题 |
| 审查方案 | 校验并编译候选方案 | 可编辑、分组、带来源的方案 | 检查关键科学选择 |
| 启动计算 | 检查当前版本，记录批准并创建运行 | 明确的启动操作和结果 | 点击“确认并启动计算” |
| 查看结果 | 注册产物，汇总自动 QC | 结果图、QC 与后续操作 | 查看结果，按需要进行科学审查 |

数据、授权和科学参数均齐全时，主路径为：提交目标 → 系统检查并准备方案 → 用户审查并启动 → 自动呈现结果。不要为签发口令、登记版本、生成哈希分别增加聊天轮次。

用户已经明确指定且没有变化的选择应持续有效。若输入或参数改变，则展示影响和差异，对新版本执行必要审查。

## 3. 对话输出：先解释结果，再给需要处理的问题

### 3.1 信息各归其位

| 信息 | 默认位置 |
| --- | --- |
| 任务理解、推荐理由、需要用户回答的问题 | 对话正文 |
| 当前参数、执行步骤、参数来源、本次差异 | 方案区域 |
| 当前阶段、耗时、运行操作 | 运行卡片 |
| 图像、自动 QC、下载与审查结论 | 结果区域 |
| 哈希、内部字段、工具参数、原始日志 | 可展开技术详情 |

普通回复按需呈现“本轮完成”“本轮变化”“需要决定”，不机械地每次输出全部标题。常规回复以约 150–300 个汉字为设计目标；复杂方法解释可以展开，不为了字数截断关键问题。

例如，用户说“平滑改成 6 mm”后：

> 已将结果图平滑从 4 mm 调整为 6 mm，其他参数保持原方案。参数校验已通过，可在右侧查看修改后的方案并确认启动。

上述完成与校验用语必须来自实际服务端状态。仍在校验时应明确显示“正在校验”。

### 3.2 消除后端追加噪声

停止向普通回复递归追加 `preprocessing.tr_seconds：模型建议` 一类字段清单。机器可读参数、来源和校验问题继续保存在结构化响应中，由前端按语义渲染。

禁止默认展示空对象、未启用配置子树、内部枚举数字及完整哈希。专家用户可展开技术详情检查原始配置。自然语言摘要与方案卡引用同一版本，避免分别生成而相互矛盾。

## 4. 参数来源与校验状态分开表达

参数的来源回答“这个值从哪里来”，状态回答“现在是否可靠、是否需要处理”。用户批准运行是独立的方案级记录，不能用“已核实”代替。

| 来源 | 含义 | 示例 |
| --- | --- | --- |
| 数据读取 | 从实际文件读取 | TR、时间点数 |
| 用户指定 | 用户明确选择 | Segment 标准化、平滑 4 mm |
| 系统计算 | 确定性程序计算 | 根据层时间推导层顺序 |
| 模型推荐 | 模型提出的待审查分析选择 | 用户未指定时的去噪建议 |

可展示的审查状态为：已核实、待选择、存在冲突、已纳入运行方案。必要时同时显示来源和校验依据，例如“参考层 33 · 用户指定 · 已通过范围检查”。“用户指定”不代表它自动通过科学约束校验。

规则：

1. 用户明确指定的参数进入持续约束，模型不能静默替换或增加指标。
2. TR、时间点数、层时间排序、参考层索引等由确定性代码读取或计算；引用有效不等于数值推导正确。
3. 模型使用语义值，例如 `t1_segment`、`friston_24`；应用层负责映射到受支持的 DPABI 枚举，不要求用户理解数字代码。
4. 冲突显示实际事实、当前选择和可行操作。例如：“文件包含 240 个时间点，方案填写 234。请确认是否需要裁剪，或将方案改为全部时间点。”
5. 无可靠证据时明确标记待核实，不能把推测写成扫描元数据。

## 5. 方案审查界面

### 5.1 布局与入口

桌面采用可展开的宽侧栏；窄屏进入独立的全屏方案审查视图。对话中保留简洁方案卡作为入口，不自动弹出遮挡长对话的大弹窗。

方案区域包含五部分：

1. **概要**：任务标题、受试者数量、当前方案版本、就绪状态。
2. **输入**：功能像与 T1 配对、TR、时间点数、起始阶段与证据。
3. **执行流程**：按实际启用顺序展示步骤，清楚区分指标计算与结果图平滑。
4. **关键参数**：中文名称、数值、单位、来源、校验状态、编辑入口。
5. **输出与 QC**：预期产物，以及本次运行选择的 QC 审查方式。

默认只展开影响科学解释和执行的关键项。高级参数按阶段折叠；未启用项以一句话呈现，不展开空配置。历史方案默认收起并只读，明确显示对应版本和运行。

### 5.2 编辑与反馈

- 支持在参数位置直接编辑，也保留自然语言修改。
- 编辑后显示旧值 → 新值及受影响步骤；新版本通过校验后才能启动。
- 阻断问题紧邻字段显示，顶部给出问题数量，点击可定位。
- 保留未提交输入；关闭审查视图不丢失草稿。
- 仅一个确定选项时，不增加无意义的单选框。
- 使用可键盘操作的控件、明确焦点和文字状态，不能仅靠颜色表达错误。

底部固定动作随状态变化：

| 状态 | 主操作 |
| --- | --- |
| 缺少必要信息 | 补充必要参数 |
| 存在阻断冲突 | 查看并解决问题 |
| 正在校验 | 显示正在进行的检查，防止重复提交 |
| 方案就绪 | 确认并启动计算 |
| 暂不启动 | 保留方案 |

## 6. 确认机制与性能

### 6.1 统一确认，保留执行边界

参数齐全后自动校验、编译并展示可审查的不可变方案版本。最终界面清楚呈现输入范围、科学步骤、QC 选择与真实执行含义。用户点击“确认并启动计算”后，服务端核对版本、记录批准并创建运行，无需再经过模型理解一次启动意图。

哈希、一次性授权挑战、乐观并发校验和幂等键由系统传递。用户默认看到“方案第 3 版”，无需手输哈希或技术口令。方案已经改变时拒绝旧版本启动，并展示差异，引导审查新版本。

起始阶段仍必须来自用户明确选择和服务端冻结。可将选择放入方案审查控件，减少重复询问，但不能用模型推断代替用户确认。文件访问授权继续绑定实际工作区、模型与配置修订。

该设计涉及确认交互和可能的授权接口调整。实施前核对 ADR 0015、0017、0018；若改变既定合同，应新增后继 ADR 并链接历史记录，不能直接把旧决策改写为新事实。EXECUTE 不进入模型工具目录的边界保持不变。

### 6.2 减少重复工作

分别记录模型响应、文件读取、事实推导、校验、哈希、编译和排队耗时，定位实际瓶颈。以测量结果决定缓存位置，不预设哈希就是主要问题。

普通对话和无关参数修改不应触发全量影像扫描。缓存按输入标识和修订失效；元数据快速检查不能替代必要的完整性保证。冻结输入及启动前仍按合同执行完整性检查，并将耗时作为独立步骤呈现。

## 7. 失败恢复

| 情况 | 用户看到 | 系统处理 |
| --- | --- | --- |
| 元数据读取失败 | 哪项信息尚未读取，以及重试入口 | 保留已验证草稿，重试必要读取 |
| 模型输出截断或格式非法 | 本轮方案未能整理完成 | 保留原方案，可重试当前整理步骤 |
| 证据引用失败 | 哪个结论尚不能采用 | 有界修复引用或请求重试，不接纳无证据事实 |
| 科学参数冲突 | 两个值、影响和可选处理 | 定位字段，等待明确选择 |
| 输入文件改变 | 哪些输入变化、哪些结论失效 | 重新核实相关内容并生成新版本 |
| MATLAB 运行失败 | 失败阶段、可理解原因、日志入口 | 保留产物和诊断，修复后由用户明确发起新运行 |
| 启动请求响应丢失 | 正在确认运行是否已创建 | 通过幂等键查询已有运行，不重复启动 |

自动重试只用于有界的只读操作或格式修复。超过次数或时间预算后明确呈现可继续的下一步，不进入重复调用循环。用户不应需要提供工具名、内部字段或 JSON 才能恢复。

## 8. 长任务与结果体验

运行卡片显示真实阶段、已完成步骤、已耗时和操作。例如“正在进行 T1 分割，已运行 6 分 20 秒”。缺少可靠估计时，不显示虚构百分比或预计完成时间。

“停止等待回复”和“取消计算”分开命名与处理。取消必须反映 Worker 的实际结果，不能因前端停止轮询就宣称运行取消。

运行结束自动出现结果卡，展示：

- 计算完成时间、指标产物和图像预览；
- 自动 QC 指标与仍需人工检查的内容；
- 对应方案、输入谱系、日志和下载入口；
- 下一步操作，如进行 QC 审查或开始后续分析。

“计算完成”与“QC 审查通过”分开呈现。处于 `qc_review` 的运行不能显示为科研审查已通过。刷新、重新打开会话后恢复真实运行状态，用户无需再问“做完了吗”“结果在哪里”。

响应契约应分别承载对话正文、方案修订引用、变更摘要、校验问题、待回答事项与可执行界面动作。具体字段在实施时通过类型定义和 API 契约确定，不另建一套独立于现有方案和运行的状态机。

自然语言中的数值取自已核实事实；“准备完成”“已排队”“正在运行”“待 QC 审查”统一术语并由服务端状态驱动。

## 10. 实施顺序

| 阶段 | 工作包 | 完成标准 |

## 11. 验收与观察指标

### 11.1 必须通过的交互场景

1. 参数与数据齐全：用户以科研自然语言提出完整 ALFF 请求，经审查按钮启动，无需补充字段名或工具指令。
2. 单参数修改：平滑 4 mm 改为 6 mm，显示准确差异，其他明确选择不改变。
3. 缺失与冲突：只询问必要信息，问题可定位；冲突消除前不能启动。
4. 输出或读取失败：保留有效草稿，有界重试，不把失败轮次当作成功更新。
5. 版本并发：旧方案确认被拒绝并显示新版本差异；不能批准未展示的修改。
6. 双击、网络断开与刷新：只创建一个运行，重连后能恢复状态。
7. 运行失败与取消：展示实际状态和恢复入口，停止前端等待不误称取消计算。
8. 结果与 QC：正确区分计算完成、待审查和审查通过，能追溯批准方案及产物。

## 12. 边界与实施风险

本次设计不会取消科学校验、数据只读约束、输入完整性、用户执行确认或可复现记录。隐藏技术细节应降低用户负担，不能隐藏冲突或不确定性。

主要风险是摘要与实际配置不一致、缓存未正确失效、旧版本被确认，以及前端和后端状态分离。分别通过单一结构化事实来源、修订绑定、服务端校验与持久化状态恢复控制。

实施以本计划的阶段验收为准；只有完成对应实现和验证后才更新状态。未完成的能力继续标记为计划内容。
